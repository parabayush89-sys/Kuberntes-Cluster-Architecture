01 · Kubernetes — the big picture

Kubernetes (often shortened to K8s) is a container orchestration platform. It manages containerized applications across a cluster of machines.

Cluster behaviour

Workloads run across a group of nodes rather than being managed as isolated containers on one machine.

Self-healing

Kubernetes works toward the declared desired state, replacing or recreating failed Pods when managed by controllers.

Scaling

Workloads can be scaled by changing replica counts; autoscaling can adjust capacity when configured.

Platform features

Networking, service discovery, access control, security integrations, and cloud-provider integrations support production workloads.

Remember: Kubernetes does not simply “run a container.” It coordinates the desired state of workloads across a cluster.

02 · Docker vs Kubernetes

The transcript introduces Kubernetes by comparing a simple container run with a Pod scheduled and managed in a cluster.

Docker (simplified comparison)Kubernetes
Basic deployment unit: containerBasic workload unit: Pod (one or more containers)
Container engine/runtime runs containers on a hostWorker node uses kubelet and a CRI-compatible container runtime
Container management is generally host-focusedCluster control plane coordinates workloads across nodes
Scaling and recovery need additional tooling or configurationControllers maintain desired state; scaling features can be configured
Pod = wrapper around containers. A Pod provides a shared execution context for its containers, including network identity and optionally shared storage.

03 · Kubernetes cluster architecture

A Kubernetes cluster is commonly explained as two logical parts:

Cluster overview · control plane directs, worker nodes execute

Control Plane

Makes cluster-level decisions: accepts API requests, stores cluster state, schedules Pods, and runs controllers.

Data Plane / Worker Nodes

Runs application workloads: hosts Pods and provides node-level services needed to run them.

Diagram is conceptual: real clusters may have multiple control-plane nodes, many workers, and additional networking/storage components.

04 · Kubelet — the node agent

Where? Runs on every worker node (and also on control-plane nodes that are configured to run kubelet).

  • Communicates with the API server.
  • Ensures the containers described by assigned Pod specifications are running and healthy, using the container runtime.
  • Reports node and Pod status back to the control plane.
Memory hook: kubelet = node agent that makes the assigned Pod specification happen.

05 · Kube-proxy — Service networking

  • Runs on nodes and implements Kubernetes Service networking behaviour.
  • Programs network rules so traffic destined for a Service can be directed to an appropriate backend endpoint.
  • Traditionally uses iptables or IPVS; modern clusters may use other implementations or replace kube-proxy functionality.
Do not mix these up: Pod IP allocation is generally handled by the cluster's CNI network plugin. Kube-proxy is mainly associated with Service virtual IP / traffic forwarding behaviour.

06 · Container runtime

The runtime is the software that actually starts and manages containers on a node.

kubelet→CRI interface→Container runtime→Containers

Examples include containerd and CRI-O. Kubernetes talks to runtimes through the Container Runtime Interface (CRI).

Historical note: The transcript mentions Docker shim. Kubernetes removed its built-in dockershim in v1.24. Docker Engine can still be used with Kubernetes through an appropriate CRI adapter, but Docker is not required.

07 · API server — the front door

The API server exposes the Kubernetes API and is the main entry point for requests from users, automation, and cluster components.

  • Receives and validates API requests.
  • Performs authentication, authorization, and admission processing.
  • Reads and updates cluster state in etcd.
  • Provides the API through which components communicate.
Interview line: kube-apiserver is the front end of the Kubernetes control plane.

08 · Scheduler — chooses the node

The scheduler watches for Pods that have not yet been assigned to a node, evaluates eligible nodes, and selects a suitable node.

  • Considers resource requests and constraints such as affinity, taints, and tolerations.
  • It selects a node; kubelet on that node then works with the runtime to start the Pod's containers.
Pending Pod→Scheduler evaluates nodes→Node selected
Remember: Scheduler decides where a Pod should run. It does not itself start the containers.

09 · etcd — cluster data store

etcd is a consistent, distributed key-value store used by Kubernetes to persist its cluster state and configuration data.

  • Stores Kubernetes API data such as objects and their desired configuration.
  • It is critical to cluster recovery; protect it with secure, tested backups.
  • Access should be tightly restricted because it contains sensitive cluster data.
Memory hook: etcd = persistent key-value store for Kubernetes cluster state.

10 · Controller manager

The controller manager runs control loops. A controller continuously compares the desired state with the observed state and takes action to move the cluster toward the desired state.

Controller reconciliation loop

Example — ReplicaSet controller: if the desired replica count is 3 but only 2 matching Pods exist, the controller works to create another Pod.

Key phrase: Kubernetes controllers are reconciliation loops — they keep working to match actual state to desired state.

11 · Cloud controller manager (CCM)

Used when Kubernetes integrates with a cloud provider. It contains cloud-specific control logic so Kubernetes can interact with provider services.

  • Can manage or coordinate cloud load balancers for Services.
  • Can integrate node information and routes with the cloud provider.
  • Can support cloud storage integrations through related provider components.
On-premises clusters: a cloud controller manager may not be needed when there is no cloud-provider integration to manage.

30-second answer: The Control Plane manages the cluster. The API server is the entry point, etcd stores state, the scheduler chooses nodes, and controllers reconcile desired state. Worker nodes run Pods using kubelet and a container runtime; kube-proxy or an alternative networking implementation handles Service traffic.

14 · Important modern accuracy notes

The transcript is a beginner-friendly explanation. These clarifications help keep your notes technically accurate for current Kubernetes:

  1. Docker shim is historical. Kubernetes removed dockershim in v1.24. Current clusters commonly use containerd or CRI-O through CRI.
  2. CRI means Container Runtime Interface. It is the interface between kubelet and the container runtime.
  3. Kubelet does not ask a central component to restart every failed Pod. Kubelet manages containers for Pods assigned to its node and reports status. Higher-level controllers such as Deployments / ReplicaSets replace missing Pods to maintain desired replicas.
  4. kube-proxy does not normally allocate Pod IP addresses. Pod networking and IP allocation are typically provided by a CNI plugin. kube-proxy implements Service networking when the cluster uses it.
  5. Scheduler selects; kubelet runs. These are separate responsibilities and a common interview distinction.
Exam tip: If your course instructor uses a simplified analogy, understand the analogy first — then use these clarifications when explaining a real Kubernetes cluster.

15 · Practice assignment

Use these tasks to turn the architecture into practical understanding.

  1. Draw the Control Plane and two Worker Nodes. Label every component.
  2. Explain the path of kubectl apply -f pod.yaml from request to running Pod.
  3. Write one sentence each for kubelet, kube-proxy, container runtime, API server, scheduler, etcd, and controller manager.
  4. Create a Deployment with 3 replicas. Delete one Pod and observe how the ReplicaSet restores the desired count.
  5. Inspect your cluster with kubectl get nodes, kubectl get pods -A, and kubectl describe pod <pod-name>.
  6. Write a short GitHub README explaining the architecture and share the diagram with your study notes.
Self-check: Can you explain why Kubernetes needs both a Control Plane and Worker Nodes without simply memorizing component names?
